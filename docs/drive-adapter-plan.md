# Accepted provider change and bounded Drive adapter plan

2026-10-02. User chose Google Drive for PDF originals. Supabase remains the source of truth for papers, chemistry, experiments, conditions, evidence and revision history. This is an implementation plan for PM review, not configured OAuth or a live upload feature. No PDF migrations/buckets were applied remotely, so no cleanup or deletion is required.

The former Task 3 Supabase Storage candidate is retained byte-for-byte under `supabase/superseded/`, outside the active migration path. Its runtime remains disabled and its private-view endpoint now fails closed too. The old review artifact is historical. Do not apply it or provision its verifier role. Active Task 4 tests run directly after the accepted metadata migrations, without Storage tables or the superseded PDF migration.

## Next bounded implementation

1. Introduce a provider-neutral document receipt through a NEW reviewed migration. Proposed receipt fields: provider (`google_drive`), internal asset ID, file ID, observed headRevisionId, server-derived SHA-256/byte count, import time, original filename and acquisition provenance. Preserve legacy Supabase fields only as a legacy provider variant, not as mandatory permanent location fields. Existing source-anchor IDs remain internal references; confirmation stays disabled until the neutral document/analysis bridge exists.
2. Bind one private app-created Drive folder to the authenticated owner's integration. Request `drive.file` only. Existing files require explicit selection when necessary; choosing a folder must not be treated as authority over every existing/future descendant. The connected dot Drive tools are not this custom web application's OAuth grant. [Drive scope guidance](https://developers.google.com/workspace/drive/api/guides/api-specific-auth)
3. Start a resumable upload for each intent/edition, creating a separate original file rather than updating an old edition. Mobile/desktop browsers send chunks directly to Drive; Vercel handles identity, intents and completion metadata, never a large PDF request body. The exact browser CORS/session authorization and interrupted-session recovery flow must pass a small synthetic probe before feature claims. Refresh tokens stay server-side; no token/session URI is logged or placed in Git. [Resumable upload guidance](https://developers.google.com/workspace/drive/api/guides/manage-uploads)
4. Completion accepts an intent ID, not a client-certified hash or page count. Server-side bounded streaming of the selected stored bytes computes size/SHA-256 and checks the PDF header with timeout/byte limits. Record `stored_unparsed`, with no verified_at, page count or parser version. UI says 保存済み・未解析. Header/hash screening does not prove a valid, safe or parsed PDF. Missing/transient transport leaves an attempt retryable; invalid retained bytes are a distinct state. Retain mismatches/orphans for recovery, with no permanent cleanup.
5. Later analysis appends a record keyed to asset ID and exact content hash. Parsing/page/passage validation is separate from storage receipt and human scientific review. No full pdf-lib parse/decompression runs during ingestion, no paid Sandbox/new processing service is proposed, and analysis stays not_requested until a real job is queued. Evidence/page claims remain drafts until the reviewed source-analysis and human-review gates pass.

## Identity, changes and downloads

Drive is not immutable or WORM. File ID alone is insufficient. Record the observed content revision and SHA-256, detect replacement/deletion, and preserve old receipts without rewriting their provenance. File version can change for metadata; content hash distinguishes byte identity. Revision retention/keepForever has limits and cannot prevent owner deletion. Detection cannot recover a deleted original. [Revision guidance](https://developers.google.com/workspace/drive/api/guides/manage-revisions)

Default to an authorized attachment download, with fresh app authorization and source-version checks. Do not use a public sharing link. Decide and test Drive's authenticated browser download/revision route without proxying a 100 MB response through Vercel. Block unavailable/changed sources rather than silently serving a different edition. Inline viewing stays disabled until a verified PDF can be served on a separate origin with appropriate PDF headers and no HTML fallback. [Download guidance](https://developers.google.com/workspace/drive/api/guides/manage-downloads)

[Web-server OAuth](https://developers.google.com/identity/protocols/oauth2/web-server), [token expiration](https://developers.google.com/identity/protocols/oauth2)
- Current quota is unknown. After the app's own OAuth, read `about.get` storageQuota/maxUploadSize. The user's proposed 100 MB can be a target of **100,000,000 bytes**, not 100 MiB, only after quota and browser/server limits are verified. Keep the cap configurable and display exact units. Supabase's Free Storage per-file cap no longer governs Drive objects. No paid upgrade is authorized. [About resource](https://developers.google.com/workspace/drive/api/reference/rest/v3/about)
- Receipt finalization needs a narrow trusted capability: NOLOGIN/NOBYPASSRLS function owner and a separately approved future worker connection with CONNECT/private-schema USAGE/EXECUTE only. No owner membership/SET ROLE, direct table writes or broad service-role app CRUD. No login credential is generated or configured by this work.

Acceptance tests for that next slice: wrong account/project, missing/replaced/deleted revision, identical and different-byte retries, expiry/cancel/double tap, interrupted resumable upload, upload-success/DB-failure recovery, missing/transient-object retry, quota/limit refusal, authenticated attachment behavior and mobile interaction.
