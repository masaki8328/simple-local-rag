# Task 3 — private PDF acquisition, local review candidate

The local implementation includes a dedicated PDF-needed queue, paper-detail upload/recovery components, a server-only acquisition service, user-scoped Supabase repository/Storage adapters and an additive migration. Production upload/finalization deliberately returns UNCONFIGURED. A scoped verifier capability has not been provisioned or wired. This is a tested local foundation, not a working hosted upload feature.

## Lifecycle and scientific meaning

1. Owner begins a 24-hour upload_intent for an active paper/project, with an idempotency UUID, filename, expected size, optional comparison hash, edition label, source and access basis. Reusing a key with different metadata conflicts. The intent's source describes acquisition; it does not prove scientific identity.
2. Original bytes use research-originals/{project UUID}/{intent UUID}/original.pdf. The bucket is private. INSERT must match an awaiting, unexpired intent owned by the caller. RLS restricts reads to the project owner and forbids UPDATE/DELETE of research objects, even alongside broader permissive policies. No upsert, replace, copy or permanent cleanup operation is provided.
3. The server reads the actual stored bytes with a byte cap and network timeout. It checks PDF structure, rejects encrypted/unparseable/empty documents, and derives SHA-256, byte size, MIME and physical page count with pinned pdf-lib 1.17.1. A submitted hash is only a comparison constraint. Upload retry also compares the submitted bytes' server-computed hash with stored bytes. No original PDF is reserialized.
4. The trusted finalizer transaction locks the project and inserts a verified immutable document_asset and immutable paper_document link, then marks the intent finalized. It checks active owner/paper scope again. Duplicate project/hash values reuse an asset; same-paper/same-byte attempts reuse its link. Different papers may link the same bytes without being merged. The attempt retains its own source and edition metadata even when a prior immutable link is reused. New bytes create another immutable asset/version.
5. Failed verification, mismatches, cancellation, expiration and DB-finalization failures never delete stored objects. Failed-state retries re-read retained bytes without attempting an INSERT that RLS would refuse. A DB failure after upload permits later finalize replay. Invalid or different replacement bytes require a new intent/path. Cancel and finalize are serialized, and successful finalization cannot be cancelled. Upload-intent state changes enter the append-only audit table.
6. Private view requests verify session, project ownership and paper-to-asset linkage on every signing request. The app requests a 60-second signed URL and sends private/no-store and no-referrer response headers. Signed URLs are bearer links until expiration; issuing a new one requires fresh authorization. User-accessible Storage APIs may also issue owner-authorized URLs, so the application TTL is not a global cryptographic limit on every URL an owner could mint.

Physical page count is the server parser's page-tree count over original bytes. Physical page positions are 1-based, independent of printed page labels (Roman numerals, article numbering, etc.). Printed labels are not inferred. Parsing does not certify a passage, scientific claim, paper identity or human review. No source_anchors or human-verified statuses are created. Same-document/acyclic anchor supersession remains future acceptance, not a new guarantee.

## Privileged boundary and blockers

The ordinary user client can begin/cancel intents and upload/read owner-scoped objects. It cannot insert assets/documents, invoke the private finalizer or claim verification. kg_pdf_verifier is NOLOGIN/NOINHERIT/NOBYPASSRLS, owns no tables, has no auth-schema USAGE and receives no application-role membership. Its narrowly granted asset/document INSERT and intent-result UPDATE remain subject to owner RLS. The private finalize function is SECURITY INVOKER; public client roles cannot execute it. Existing administrator audit/identity helpers remain the only bridge to auth.uid.

`productionPDFService()` unconditionally fails closed. There is no enabling environment flag, fabricated user, service-role fallback or credential value. `TrustedFinalizer` is an internal trusted callback contract, not a public endpoint that may accept client hash/page counts. A future worker must independently verify the user's JWT and bind the SQL transaction's caller identity to the verified subject. If a network boundary exposes verification fields, the worker must re-read and recompute the object data itself. Provisioning a scoped login/worker capability requires separate review; no such persistent access was created here.

Activation also requires isolating PDF parsing with hard CPU/time/memory limits. Current local parser tests have a 4 MiB input cap and 2,000-page postcheck, which do not bound decompression or pathological page-tree CPU. Do not enable this parser in a public request process before that worker boundary exists. Parsing is not malware sanitization.

Hosted Storage DDL compatibility is unverified: the local shim gives postgres ownership of storage tables to exercise real RLS/policy evaluation. Root must check actual Storage table ownership/role eligibility and bucket privileges before applying the candidate. Metadata initialization authorization is not Storage/worker provisioning authorization. See hosted-migration-map.md before any CLI push; do not reapply accepted metadata history.

## UI and limits

Queue entries show title, authors/year, DOI, source URL, priority, investigation reason and an explicit Research Question placeholder. Missing values remain unknown/unregistered. The new authors column is empty by default; broader metadata editing/provider acquisition is outside this slice. The queue removes a paper when a main-text paper_document links a verified asset, not merely because an upload attempt exists.

File inputs are present on the queue and paper detail. The component implements progress, pending/double-tap protection, draft retention, retry, cancellation and success-to-new-edition reset. Detail shows attempt state/expiry and retained-object re-verification controls. Production controls explain that setup is pending and remain disabled. Browser tests exercise enabled components only in a separate synthetic harness, not a production bypass.

`PDF_MAX_BYTES` may lower the application limit from 4 MiB (4,194,304 bytes), with 1 KiB minimum and a hard 4 MiB ceiling. The reviewed bucket and DB ceiling is also 4 MiB; lowering the app value does not alter direct Storage bucket limits. A future reviewed migration is needed to align a lower bucket cap. The ceiling is conservative for raw-body Vercel requests, not a tested hosted capacity promise. [Vercel limits](https://vercel.com/docs/functions/limitations) and [Supabase standard uploads](https://supabase.com/docs/guides/storage/uploads/standard-uploads) were checked.

The user-selected Free-plan 1 GB storage budget includes retained failures and duplicate attempts. No automatic deletion, quota reservation, billing change or storage upgrade is implemented. Actual free capacity and hosted upload limits must be checked before activation. Larger PDFs/resumable upload and cleanup require later reviewed work.

## Verification and remaining live tests

Synthetic PDF bytes are generated in memory at test runtime; no PDFs, research passages, credentials or private records are tracked. Tests cover actual-byte/hash mismatch, malformed/non-PDF/oversize, expiration, cancellation, cross-project paths, immutable objects, duplicate bytes, repeated finalize, failed-object retry and upload-success/DB-failure recovery. Real isolated PostgreSQL tests cover RLS and two concurrent finalization cases. SDK adapter tests instantiate real StorageApiError shapes for current and legacy duplicate responses; generic 400 is refused.

The Storage table shim is not an object server. Live JWT/Storage upload semantics, bucket size/MIME enforcement, concurrency across actual object writes, signed-URL expiration at the service, denial/revocation and mobile authenticated navigation remain untested. Local URL tests check the requested TTL and refusal behavior only. Do not describe them as live expiry tests.
